# ShenZhi 文档目录说明

本目录用于维护 ShenZhi 的产品、工程、设计、模块说明与开发相关文档。

新增或维护文档时，应优先放入对应分类目录，避免无明确归属的文档长期直接堆放在 `docs/` 根目录。

## 目录说明

```text
docs/
├── engineering/     # 全局工程架构与开发规范
├── auth/            # 登录、注册、认证与账号体系
├── chat/            # AI 对话模块
├── logging/         # Logging Core 与异常观测
├── design/          # 产品视觉、品牌与设计规范
├── dev/             # 阶段性开发记录与历史开发资料
├── prd/             # 产品需求文档
├── prototypes/      # 页面或交互原型
└── ...
```

### `engineering/`

维护项目级工程文档，例如：

* 总体工程架构
* 模块边界
* 前后端职责划分
* 目录与代码组织规范
* 公共技术决策

项目整体架构相关内容应优先维护在此目录。

---

### `auth/`

维护用户认证与账号相关文档，例如：

* Auth 架构
* 登录 / 注册流程
* Better Auth 配置
* 邮件与验证码
* 认证相关维护说明

---

### `chat/`

维护 AI 对话模块相关文档，例如：

* Chat 当前实现说明
* 前后端协议
* 数据与状态流
* 迁移记录
* 验证与维护说明
* 浏览器手工走查：`docs/chat/BROWSER-WALKTHROUGH.md`

---

### `logging/`

维护 Logging Core 与异常观测说明，例如：

* 实现基线：`docs/logging/README.md`
* 两人分工与合入进度：`docs/logging/分工.md`

Logging 不改 Chat 状态机、错误码或 BFF fail-closed。

---

### `design/`

* 品牌规范
* 配色
* UI / UX 设计规范
* 视觉资产说明

---

### `dev/`

维护阶段性开发资料和历史记录，例如：

* 阶段性说明
* 临时开发记录

该目录主要用于保留开发过程信息，不应作为当前正式工程规范的主要来源。

### `prd/`

## 业务模块文档

当某个业务模块形成较稳定、较完整的开发与维护内容时，可以建立独立目录，例如：

```text
docs/
├── knowledge/
├── deep-research/
├── auto-research/
└── ...
```

其中可维护：

```text
README.md
API.md
ARCHITECTURE.md
MIGRATION.md
VALIDATION.md
```

具体文件按实际需要建立，不要求所有模块采用完全一致的结构。

如果子功能文档较少，也可以直接通过清晰文件名维护；文档较多时再建立子目录。

---

## 文档维护原则

1. `docs/` 不要求与代码目录严格镜像，但应保持一致的业务语义。
2. 项目级工程规范统一放入 `engineering/`。
3. 具体业务实现说明优先放入对应业务目录。
4. 阶段性记录与正式维护文档应区分，历史开发资料优先放入 `dev/`。
5. 不为追求目录完整性创建无实际内容的空目录。
6. 核心架构、接口或业务边界发生实质变化时，应同步更新相关文档。
7. 新增文档前先确认是否已有对应目录或已有文档可以继续维护，避免重复建立相同职责的说明。

当前 `docs/` 根目录中的业务说明文件应逐步整理至对应业务目录，根目录原则上只保留本说明及确有全局意义的文档。

# 会议自动同步代码审查与修复

日期：2026-11-04；本地分支 feat/conference-sync。审查范围为相对 dev 的会议同步实现、缓存/存储、关注迁移、后台调度、页面刷新及相应测试。未上传、推送、部署。

## 结论

发现并修复 3 个功能/防护缺口，另修正 1 处事件循环阻塞风险。真实 GitHub 自动同步、数据库竞态和缓存读写检查通过。当前可供本地演示和代码评审；生产长驻调度环境、生产迁移、连续 24 小时耐久及生产负载未验收，不据此宣称生产已就绪。

## 已修复

### P1：关注写入与快照发布之间存在竞态

原实现先查询关注，再单独提交快照；同时关注旧会议的请求还可能使用最长五分钟的旧缓存通过验证。快照发布和关注写入若交错，可能留下指向已移除会议的关注。

修复：短时发布事务锁与关注事务共享锁配合。发布在同一事务内重新查询关注并验证；关注拿到共享锁后，使用数据库当前 JSONB 内容再次校验 ID，而非只信缓存。下载不持有这把短锁。移除目标会返回 404；取消关注仍能释放旧记录。

代码：services/conferences_repository.py 的 save；services/library/conference_follows.py 的 follow；api/conferences.py 的错误映射。

证据：tests/test_conference_publication.py 在真实独立 PostgreSQL 上验证两种竞争顺序：发布先获得锁时旧 ID 关注被拒绝；关注先提交时发布拒绝丢失该关注。普通关注和重复关注同样通过。API 新增回归测试验证正确返回 404。

### P2：页面长期打开不会自动显示新数据

staleTime 仅标记缓存过期，不会主动每隔五分钟请求。后端同步成功后，持续打开且未触发窗口聚焦/重新查询的页面可长期显示旧数据。

修复：会议列表、分类和用户关注查询均增加五分钟 refetchInterval。后台标签页遵循查询库的默认暂停策略，返回页面时按过期策略刷新。

证据：实际浏览器中模拟五分钟，列表请求从 1 次变为 2 次，并验证页面资料日期变为第二次返回值；测试只在隔离浏览器中注入日期，没有改真实资料。

### P2：压缩包扩展元数据未计入实际解压量

原代码只在 tarfile 返回普通成员后统计大小；PAX/GNU 元数据可能先被 tarfile 消费，未进入统计。

修复：在 gzip 解压流与 tarfile 之间增加逐字节累计上限，覆盖普通内容及元数据；同时拒绝稀疏文件和负大小成员。仍保留下载、单 YAML、YAML 总量、路径、链接、重复文件及成员数检查。

证据：新增 PAX 元数据测试在修复前确实失败（未抛异常），修复后通过。修复后的读取器也通过真实 GitHub 压缩包下载、清洗、写库验收。

### 性能：完整替换校验不应占用异步事件循环

同步编排在 await 后直接执行了一次完整目录重建/时区校验。现已使用 asyncio.to_thread 执行，降低更新期间阻塞其他请求的风险；原有日期选择和筛选规则不变。

## 性能与存储核对

- 1000 次已预热缓存 get：额外数据库请求为 0；本机该轮共 1.076 ms。此数值仅是 Python 缓存访问，不是 HTTP 压测或生产吞吐量。
- 冷加载加一次到期检查：版本查询共 2 次，整份 payload 查询仅 1 次；版本没变不重新取整份资料。

- 服务端目录缓存、前端五分钟刷新和 SHA 比较分层处理，不让页面直接请求 GitHub。

2. 本地测试不是连续 24 小时运行，也不替代生产负载测试。
3. 单份快照存储是明确取舍；回滚须有备份/明确恢复源，关注 ID 合并不能无损逆推原用户选择。迁移应与新快照同批发布。
